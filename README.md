# 三阶魔方求解器（Kociemba 二阶段算法）

一个纯前端的 3×3×3 魔方求解器：Kociemba 二阶段算法求解，three.js 渲染，
支持随机打乱、一键复原、鼠标拖动转动、拖动视角与滚轮缩放。

不依赖任何求解库——坐标、剪枝表、两阶段搜索全部自己实现；唯一的运行时依赖是 `three`。

**当前构建版本：`r5-unlimited-orbit`**（显示在侧栏标题下方，也暴露为 `window.__cube.version`）

## 快速开始

```bash
npm install          # 只装 three.js
npm run serve        # 启动本地静态服务器（默认 8787）
# 浏览器打开 http://127.0.0.1:8787/
```

页面打开后会在浏览器里构建求解表（约 0.5 秒），状态栏显示「求解器就绪」即可使用。

> **改了代码但页面没变化？** 侧栏那行「构建版本」就是答案：
> 显示 `r4-rotation-baked` 说明已是新代码；显示 `—` 说明浏览器还在跑缓存的旧 JS，
> 请 `Ctrl+Shift+R` 强制刷新或清一下该站点缓存。服务端已发 `Cache-Control: no-store`，
> `index.html` 也带 no-store meta，正常刷新不会再拿到旧模块。

## 操作

| 操作 | 效果 |
| --- | --- |
| 在魔方表面按住拖动 | 转动手指所在的那一层（贴纸跟着手指走） |
| 在空白背景按住拖动 | 旋转视角 |
| 滚轮 | 缩放 |
| 随机打乱 | 生成 20 步随机打乱并播放动画 |
| 求解并复原 | 计算解并逐帧播放复原过程 |
| 复位 / 撤销一步 | 回到复原态 / 回退一步 |
| 手动转动按钮 | U U' R R' F F' D D' L L' B B' |

拖动语义：**在哪个面上拖，就转那个面所在的层**（与真手手感一致）。方向由投影决定——
把抓取点按 ±90° 真实旋转后投影到屏幕，取与鼠标位移同向的那个方向，因此贴纸必然跟手，
且「拖哪个面就转哪个面」不会有歧义。

## 算法

### 二阶段分解

**第一阶段** 把魔方送入子群 `G1 = <U, D, R2, F2, L2, B2>`，即在坐标
`(twist, flip, slice1)` 上到达 `(0, 0, 0)`。此时所有角块与棱块朝向正确，
四个中层棱块也回到中层。

**第二阶段** 在 `G1` 内继续求解，把 `(cp, ep8, sp)` 归零，只允许
`U U2 U' D D2 D' R2 F2 L2 B2` 这 10 种转动。

两阶段都是迭代加深 DFS（IDA*），启发函数取各坐标精确距离表的**最大值**——
每个表都是剩余步数的下界，取最大仍可采纳，因此不会漏掉最短解。搜索带墙钟时间上限，
保证不会卡死。

### 坐标

| 坐标 | 取值范围 | 含义 |
| --- | --- | --- |
| `twist` | 0..2186 (3⁷) | 角块朝向（第 8 块由约束推出） |
| `flip` | 0..2047 (2¹¹) | 棱块朝向（第 12 块由约束推出） |
| `slice1` | 0..494 (C(12,4)) | 四个中层棱块所占的位置组合 |
| `cp` | 0..40319 (8!) | 角块排列 |
| `ep8` | 0..40319 (8!) | 上/下层棱块在槽位 0..7 内的排列 |
| `sp` | 0..23 (4!) | 四个中层棱块在槽位 8..11 内的排列 |

排列用字典序 rank/unrank，位置组合用 colex rank/unrank；`slice1` 与 `sp` 的镜像处理
保证**复原态在所有坐标上都是 0**。

### 剪枝表

从目标态出发做 BFS 精确填表（得到的是最短距离，不是估计值）：

| 表 | 规模 | 最大距离 |
| --- | --- | --- |
| `flip × slice1` | 1,013,760 | 9 |
| `twist × slice1` | 1,082,565 | 9 |
| `cp × sp` | 967,680 | 14 |
| `ep8 × sp` | 967,680 | 12 |

覆盖率经检查为 **100%**（无未填充格子），所以启发值从不高估。

### 实测性能

环境：Node v22，建表与求解均在 JS 内完成（`test:unit` + `test:solver` 的实测值）。

| 指标 | 数值 |
| --- | --- |
| 建表时间 | ~0.5 秒 |
| 平均求解时间 | ~260 ms |
| 最坏求解时间 | ~1.8 秒 |

## 实现要点

以下几处是真正踩过坑的地方，也是回归测试重点守住的地方。

### 1. 转动必须烘焙进小方块

贴纸是**小方块的子网格**，固定在局部坐标上；动画用的临时 `Group` 在重新挂回根节点时
会被丢弃。因此每步落地时必须把这一转的四元数 `premultiply` 到小方块自身：

```js
const qTurn = new THREE.Quaternion().setFromAxisAngle(AXIS_VEC[k], q * Math.PI / 2);
g.quaternion.premultiply(qTurn);
g.quaternion.copy(snapQuaternion(g.quaternion));   // 吸附到 24 个标准朝向，防漂移
```

若写成 `g.quaternion.identity()`，网格会弹回建模朝向，而 `ori`（朝向记录）仍记着转动——
两者错位就会让贴纸对不上，**露出深色本体面**（"色块消失"）。

`test/viewrender.test.mjs` 用真实 three.js 对象，从场景图反查「每个可见方向上实际是哪个
网格」来守住这一点。注意不能读渲染时自己写的那套记录——那种自证永远查不出这个 bug。

### 2. 四分之一转可能是负数

`turnQuarter()` 对 **U / R / F 顺时针**和 **D / L / B 逆时针**返回 **-1**。任何写成

```js
for (let i = 0; i < q; i++) { ... }   // q = -1 时一次都不执行
```

的位置更新都会对**一半的转动**静默失效：`pos` 不更新、`ori` 却照常更新，错得更彻底。
位置更新统一走 `advanceSlot(pos, k, quarter)`，它先把 `quarter` 规范到 0..3 再循环。
`viewsync.test.mjs` 里有一条专门的负角度守卫，断言 `advanceSlot` 与权威的 `rotVec` 在所有
轴与正负角度下逐一对拍，并额外断言「负的四分之一转必须真的移动非轴心方块」。

### 3. 拾取用世界坐标

判断用户点到了哪一面，用的是「命中点 − 小方块中心」在**世界坐标**下的主分量，而不是
小方块的局部坐标——转过的小方块局部轴已经不再与世界轴对齐。

### 4. 每步回调随队列项走

模型在**每一步**落地时推进，而不是整批动画结束时只看最后一步。回调跟着队列项走
（`enqueue(move, { onDone })`），所以 20 步打乱后模型与视图完全一致。早期实现用单个
`view.onMoveDone`，每调一次 `turn()` 就把它覆盖掉，导致 20 步打乱后模型只应用了最后 1 步，
求解器于是给出 1~2 步的"解"、看不出复原。

### 5. 单一数据源

求解器里的方块状态是唯一真相。每次转动落地后，视图从模型的 54 字符面片串重新着色，
因此「所见即求解器所见」。

### 6. 复位回到 `home` 槽位

每个小方块额外记录 `home`（建模时的规范槽位，永不修改）。`resetToSolved` 回到 `home`
并清空朝向，而不是回到当前的 `pos`——后者是打乱后的排列，配着清空的 `ori` 会立即错位。

### 7. 服务端 `no-store`

开发期浏览器缓存旧的 ES module 会造成「改了没生效」的假象，排查成本很高。服务端统一发
`Cache-Control: no-store, must-revalidate`，配合页面里的版本戳，一条信息就能区分
「代码没生效」和「真有问题」。

## 已知边界

- 只支持 3×3×3；不支持 2×2、4×4 或带图案的魔方。
- 求解在**主线程同步执行**，最坏约 2 秒会短暂阻塞 UI（已用 `setTimeout` 让出一次渲染，
  状态栏会先显示「正在求解…」）。
- 剪枝表在每次页面加载时于浏览器内重建（约 0.5 秒、约 4 MB 内存），未做持久化。
- 拖动判定阈值固定为 14px，未按设备像素比或触屏做适配；触屏可用但未专门优化。
